# 错题本 DSH 插件 — 第一轮设计文档

> 最后更新：2026-11-26  
> 状态：产品与架构讨论稿，尚未开始实现  
> 前置文档：`HANDOFF.md` 记录项目背景、多模型开发方案及已排除路线

---

## 1. 文档目的

本文定义错题本插件第一轮的产品边界、导入流程、存储方案、数据模型和验收标准，供后续设计与实现对话直接使用。

第一轮的核心目标是：

> **把手机拍摄的试卷、课本练习等图片可靠地归档到本地，生成清晰的标准化图片，并支持按学期、科目浏览。**

第一轮不是 OCR 系统，也不是错题复习系统。图片是权威资料，OCR 和其他智能功能只能作为后续附加能力。

---

## 2. 已确认的产品决策

1. **主要用户**：用户的一年级儿子。
2. **用户模型**：第一轮单用户，无登录、无权限体系、不支持多个孩子。
3. **产品形态**：首先作为 DSH Web UI 插件使用；若效果好，未来可改造为独立应用。
4. **主要输入**：手机拍摄的试卷、课本练习等图片，可能包含孩子的铅笔手写答案及教师批改。
5. **导入方式**：用户点击“导入”，选择科目和学期，再通过文件选择器选择一个或多个图片；通常从连接到电脑的手机中选择。
6. **重复处理**：
   - 文件级重复用 SHA-256 判断，完全相同的文件不重复复制；
   - 同一纸张的两次不同拍摄属于不同照片，应保留两个原件；
   - 通过视觉比较和用户确认，将不同照片归入同一个逻辑页面，避免图库中出现重复页面。
7. **第一轮范围**：图片导入、原图归档、标准化、科目/学期分类、图片查看，以及必要的导入后修正。
8. **后置功能**：复习、模拟测试、OCR、题目切分、知识点/错因分析、自动生成相似题等。

---

## 3. 第一轮用户故事

### 3.1 导入者

第一轮导入操作可以主要面向家长，不要求所有界面都适合一年级孩子独立操作。

- 我能一次选择多张手机照片，并统一指定科目和学期。
- 我只归档没有导入过的文件，不因手机文件名变化而重复复制同一文件。
- 我能判断一张新照片是已有纸张的另一张照片，还是一个全新页面。
- 即使取消后续整理，已经归档的原件也不会丢失，未完成任务可以恢复。
- 我可以旋转、裁剪、重置并重新生成标准化图片，而不损坏原件。

### 3.2 浏览者

- 我能按学期和科目浏览页面。
- 我能看到足够大的缩略图，并打开清晰的完整图片。
- 我能缩放、平移、前后翻页，读清铅笔字迹和教师批改。
- 我能查看同一页面的其他拍摄版本。
- 我能切换查看原件与标准化图片。
- 我能修改错误的科目、学期分类，或重新处理图片。

## 4. 明确不在第一轮的功能

- 登录、账号、多孩子或家长/孩子权限体系；
- 云同步、远程服务、联网依赖；
- 自动扫描整个 Windows 图片目录；
- OCR 自动识别题干、手写答案或教师批改；
- 自动把页面切成单道题；
- 题干、正确答案、知识点、错因等必填字段；
- 错题复习、间隔重复、掌握度、模拟测试；
- 自动透视矫正、自动页面检测、手写擦除、激进扫描滤镜；
- 自动合并两张内容相似但字节不同的照片；
- 为第一轮同时引入 DuckDB 与 PostgreSQL。

数据模型应给后续功能留下扩展空间，但不得因此扩大第一轮实现范围。

## 5. 总体架构

### 5.1 插件组成

```text
错题本 DSH 插件
├─ Host
│  ├─ 文件选择、哈希检查与原图归档
│  ├─ PostgreSQL 数据访问与迁移
│  ├─ 图片处理、标准化和缩略图
│  ├─ 页面、照片与分类业务服务
│  └─ 后续可提供给 Agent 的应用工具
└─ Client
   └─ DSH Web UI 中的独立插件页面
      ├─ 导入与视觉比较
      └─ 图库与图片查看
```

UI 必须调用应用业务服务，不直接编写 SQL。未来独立应用可复用业务规则和领域模型，但独立化不是第一轮的交付目标。

页面使用 DSH 当前支持的 React、slot、主题与 locale 机制，不通过 iframe 嵌入另一个应用。具体 slot、服务方法及 Client 通信方式必须在实现前用当前环境的 inspection 结果确认。

### 5.2 关键原则

1. 原件不可变，任何处理都不覆盖原图。
2. 文件哈希负责“是否见过这个文件”，视觉比较负责“是否属于同一逻辑页面”。
3. 同一逻辑页面可拥有多张原始照片，图库默认只显示一个页面。
4. 相似度只用于推荐候选，不擅自合并。
5. 业务服务统一负责数据库与文件操作，UI 不直接管理存储细节。
6. 任何失败或取消都不得破坏已经归档的原件。
7. 所有配置化路径都应可迁移，不在每条数据库记录中硬编码绝对路径。

## 6. 存储布局

### 6.1 Windows 原件目录

原件保存在 Windows Pictures 下，采用用户指定的目录结构：

```text
Pictures/
└── 错题本照片/
    ├── 数学/
    │   ├── 一年级上/
    │   │   └── *.jpg
    │   └── 一年级下/
    ├── 语文/
    └── 英语/
```

实际 Windows 用户目录和 WSL `/mnt/c/...` 映射需在实施前只读探测，不假定具体用户名。

规则：

- 只有新哈希文件才复制到所选科目/学期目录；
- 原件归档目录对应用按只读语义管理：导入只新增文件，之后不重命名、不移动、不删除、不覆盖；
- 手机源文件绝不移动或删除；
- 原件复制后再次计算哈希，确认复制完整；
- 文件名必须碰撞安全，不能信任手机文件名唯一性；
- 原文件名作为元数据保留，可使用时间戳和随机 ID/短哈希生成存储文件名；
- 不在未获用户明确授权时清理重复文件或源文件。

### 6.2 WSL 项目数据目录

标准化图片、缩略图等派生数据放在 WSL 项目目录下：

```text
<project>/
└── data/
    ├── processed/
    │   ├── standardized/
    │   └── thumbnails/
    └── transforms/       # 若变换参数采用文件存储
```

PostgreSQL 同样运行在 WSL。数据库保存元数据和文件引用，不以数据库 BLOB 作为默认图片存储方式。

数据库记录优先保存相对于可配置根目录的路径，例如：

- `originals_root` → Windows `Pictures/错题本照片`；
- `processed_root` → WSL 项目 `data/processed`。

### 6.3 备份边界

完整备份必须包含：

1. PostgreSQL 数据及迁移版本；
2. Windows 原件目录；
3. WSL 标准化图片与必要派生数据；
4. 路径根配置及存储格式版本。

标准化图理论上可由原件重建，但备份策略应明确是否包含它，不能只备份数据库就认为资料完整。

## 7. 数据库选择

### 7.1 第一轮采用 PostgreSQL（设计倾向）

用户熟悉 DuckDB/PostgreSQL 的语法、工具及数据建模。第一轮倾向使用 **PostgreSQL** 作为应用事务数据库，因为需要：

- 唯一约束和事务；
- UI 与可能的后台任务访问；
- 数据迁移；
- 原件、照片、页面与处理结果之间的关联；
- 哈希“检查并预留”的并发安全；
- 将来独立应用后端的演进空间。

DuckDB 更适合后续离线分析，不在第一轮同时引入。SQLite 部署更简单，但不符合用户已表达的技术偏好。

### 7.2 实施前待验证事项

以下不是已完成事实，需在新对话中只读检查：

- WSL 中 PostgreSQL 的版本、运行状态和连接方式；
- 是否已有专用于本应用的数据库/角色，以及是否需要创建；
- DSH Host 插件可采用的 PostgreSQL 客户端及依赖打包方式；
- 图片处理库、文件选择能力和 DSH Client/Host API；
- 数据目录与 Windows 原件根目录的实际路径。

任何数据库、角色、服务或配置的创建/修改，均须先说明动作和后果并获得用户明确同意。

## 8. 领域模型

必须区分以下概念：

```text
Document（资料）
└── Page（逻辑纸张页面）
    ├── Capture A（第一次拍摄的原件）
    ├── Capture B（同一页面的第二次拍摄）
    └── Standardized View（从某张 Capture 生成的标准化图）
```

### 8.1 Document

代表一张试卷、一组练习或有逻辑关联的一组页面。第一轮可以简单按每次导入或用户整理建立，不追求复杂组装规则。

### 8.2 Page

代表一个逻辑纸张页面，是图库展示、视觉归组和后续题目切分的基本单位。

### 8.3 Capture

代表一次具体拍摄及其不可变原件。同一 Page 可有多个 Capture；较清晰的新照片可以被选为标准化来源，但旧照片仍保留。

### 8.4 Standardized View / Asset

代表从某个 Capture 派生的标准化图片或缩略图。必须记录来源 Capture、变换版本和生成状态。

### 8.5 后续扩展

以后可从 Page 下建立零到多个 Question。第一轮不暴露或实现题目功能，但不要把每张上传图片直接命名为“错题”，否则将来一页多题、页内只有部分错题时难以迁移。

## 9. 初步数据模型

以下为概念模型，不是最终 DDL；字段类型、约束与索引需在实现任务中设计。

### 9.1 `subjects`

- `id`
- `code`：稳定标识
- `display_name`：数学、语文、英语等
- `sort_order`
- `enabled`

### 9.2 `terms`

- `id`
- `code`：稳定标识
- `grade`
- `term_number`
- `display_name`：一年级上学期等
- `sort_order`

需支持目录名 `一年级上` 到显示名 `一年级上学期` 的明确映射。可支持“未分类”，避免资料元数据不全时无法入库。

### 9.3 `documents`

- `id`
- `subject_id`
- `term_id`
- `source_type`：试卷、课本练习、练习册、作业、其他（可后置细化）
- `title`，可空
- `document_date`，可空
- `created_at`
- `updated_at`

### 9.4 `pages`

- `id`
- `document_id`
- `page_number`，可空
- `preferred_capture_id`，可空
- `status`：如待确认、已整理
- `notes`，可空
- `created_at`
- `updated_at`

### 9.5 `captures`

- `id`
- `page_id`，视觉确认前可空或配合独立待整理状态
- `sha256`：全库唯一约束
- `original_path`：相对原件根目录
- `original_filename`
- `source_metadata_json`：必要的源文件信息
- `media_type`
- `byte_size`
- `width`、`height`
- `visual_fingerprint`：具体格式待定，可拆表
- `created_at`

SHA-256 的唯一性覆盖所有科目和学期，避免相同照片换分类后再次复制。

### 9.6 `image_assets`

- `id`
- `capture_id`：派生来源
- `kind`：standardized、thumbnail；原件引用也可统一建模，但不可混淆职责
- `storage_path`：相对处理文件根目录
- `media_type`
- `byte_size`
- `width`、`height`
- `sha256`
- `version`
- `created_at`

### 9.7 `page_transforms`

- `id`
- `page_id`
- `source_capture_id`
- `version`
- `operations_json`
- `created_at`

至少记录旋转、裁剪、缩放及后续允许的调整。保存变换指令使处理可以重建和修正，而不是只留下不可解释的扁平结果。

### 9.8 完整性要求

- 每个原件哈希最多对应一个 Capture；
- 每张标准化图必须能追溯到 Page 和来源 Capture；
- 更换首选照片不删除其他 Capture；
- 页面合并不删除原件；
- 文件写入、哈希预留和数据库提交之间必须设计失败恢复；
- 同一文件的重复导入需具备并发保护，不能只依赖先查询后插入的应用层时序。

## 10. 导入契约

### 10.1 第一步：发起导入

用户点击 **导入**，在同一个导入流程中看到两个下拉框：

- 科目：数学、语文、英语……
- 学期：一年级上、一年级下……

随后出现文件选择窗口，用户定位并选择一个或多个图片，通常来自连接到电脑的手机。

本次选择为整个批次提供目标目录和默认分类，但后续确认界面允许修正个别误选。

### 10.2 第二步：哈希检查与原件复制

对选中的每个文件依次：

1. 读取并计算 SHA-256；
2. 在全库 Capture 注册表中检查；
3. 已存在：不复制，复用已有 Capture，可跳转到待确认任务；
4. 不存在：原子地预留哈希，复制到 `Pictures/错题本照片/<科目>/<学期>/`；
5. 使用碰撞安全的新文件名，绝不覆盖已有文件；
6. 校验复制后文件 SHA-256；
7. 创建/提交 Capture 元数据，再进入视觉比较。

如果复制或数据库操作失败，不得显示为成功导入。需有明确错误和可恢复状态；不得自动删除任何用户原件来“清理”。

### 10.3 第三步：视觉比较与用户确认

新归档照片进入视觉比较：

- 用视觉指纹检索可能匹配的已有 Page；
- 新旧图片并排显示；
- 默认提供“创建新页面”和“添加为已有页面的另一张照片”；
- 候选不存在时也允许手动搜索已有页面；
- 相似但确实不同的试卷必须能保持独立。

建议操作文案：

- **同一页，添加为另一张照片**
- **不同页，创建新页面**

第一轮不自动合并不同哈希的照片。

### 10.4 第四步：标准化

确认归组后：

- 选择或沿用首选 Capture；
- 对图片旋转、裁剪、缩放；
- 保存变换参数；
- 生成标准化图及缩略图到 WSL 数据目录；
- 用户可重置、重做、切换原件/标准化图；
- 不修改手机源文件和 Windows 归档原件。

### 10.5 取消与恢复

- 一旦原件成功复制，取消视觉确认不删除该原件；
- 未完成任务标记为“待确认/待整理”；
- 再次导入同一文件不重复复制，可恢复相关待办；
- 中断后应能区分：仅复制成功、Capture 已登记、页面已建立、标准化已完成等状态；
- 具体事务/补偿实现需在技术设计阶段明确。

## 11. 去重与视觉匹配规则

### 11.1 文件级去重

SHA-256 解决：

- 同一文件被重复选择；
- 同一文件被改名；
- 同一文件被复制到另一个目录；
- 同一文件被错误地换科目/学期再次导入。

### 11.2 页面级归组

同一纸张的两次拍摄具有不同字节、光线、角度和清晰度，因此 SHA-256 不足以判断。两张照片均应归档，但可属于同一个 Page。

视觉匹配可使用：

- 感知哈希；
- 宽高、比例；
- 页面特征匹配；
- 对旋转和透视有容忍度的对齐；
- 科目/学期等元数据；
- 手写和教师批改区域比较。

第一轮建议只做：

1. 感知哈希或其他简单指纹召回候选；
2. 新旧图并排；
3. 用户确认。

不能仅凭感知哈希自动合并：不同算术练习页可能版式高度相似，却题目、手写或批改不同。相同印刷页面也不必然是同一逻辑页面，不同孩子的作答在第一轮之外也应避免被错误合并。

### 11.3 清晰度和证据保留

同一页面的不同照片不是垃圾副本：一张可能更清晰，另一张可能保留更淡的铅笔字或更完整的边缘。更换标准化来源时，必须保留所有原始拍摄版本。

## 12. 图片标准化

第一轮支持：

- 手动或辅助旋转；
- 裁剪，仅保留目标纸张/区域；
- 最大边约束下的缩放；
- 可选的轻度对比度调整，默认关闭；
- 撤销/重置处理操作；
- 生成网页友好的标准化图片和缩略图。

第一轮暂缓：

- 自动页面检测；
- 自动透视矫正；
- 手写擦除；
- 可能抹掉淡铅笔字或彩色批改的强滤镜。

标准化图的验收标准不是“文件更小”，而是**人能清楚阅读所有必要 pencil marks 和 teacher corrections**。

原件、标准化图、变换参数三者均须保留明确关系。

## 13. 第一轮 UI

### 13.1 导入页/流程

- “导入”按钮；
- 科目与学期下拉框；
- 多文件选择；
- 每张文件的哈希检查、复制和处理状态；
- 精确重复提示；
- 候选页视觉比较与人工归组；
- 原件/处理图预览；
- 旋转、裁剪、撤销/重置；
- 待确认任务入口；
- 清晰的失败与恢复反馈。

### 13.2 图库页

- 学期 → 科目筛选；
- 大缩略图或紧凑列表；
- 全尺寸图片查看器；
- 缩放、平移、上一页/下一页；
- 原件/标准化图切换；
- 同一 Page 的多 Capture 查看；
- 修改分类；
- 重新裁剪、重新生成标准化图。

图库界面以大图和简单中文标签为主，为孩子使用打基础；第一轮导入和整理界面可以优先满足家长效率。

## 14. 第一轮验收标准

### 14.1 导入与文件去重

1. 点击“导入”后可选择科目、学期，并通过文件选择器多选手机图片。
2. 新文件只复制到指定的 Windows `Pictures/错题本照片/<科目>/<学期>/` 目录。
3. 同一 JPEG 再选一次，不生成第二个 Capture 或第二个原件。
4. 同一 JPEG 改名、移动或换分类再导入，仍不重复复制。
5. 文件复制后哈希一致，不覆盖已有文件。
6. 手机源文件及已归档原件不被修改、移动或删除。
7. 两个导入操作同时遇到同一文件时，最终仍只有一个 Capture。

### 14.2 页面级归组

8. 同一纸张拍摄两张不同照片时，两张原件均保留。
9. 系统能展示可能的已有页面供并排比较（候选召回效果需用真实样本测试）。
10. 用户确认后，图库只显示一个 Page，其下可查看两个 Capture。
11. 可更换首选 Capture，并据此重新生成标准化图。
12. 相似但不同的练习页可以明确创建为不同 Page，不被强制合并。

### 14.3 标准化与浏览

13. 用户可旋转、裁剪、重置图片，原件始终不变。
14. 标准化图和缩略图只写入指定 WSL 项目数据目录。
15. 标准化图在目标显示器上可清楚阅读铅笔答案和教师批改。
16. 图库可按学期、科目筛选，并支持全尺寸查看、缩放和翻页。
17. 用户可查看其他 Capture、切换原件/标准化图、修正分类和重做处理。

### 14.4 异常与数据完整性

18. 取消视觉确认不删除已复制原件，任务可在“待确认”中恢复。
19. 导入中断或处理失败不会丢失源文件，也不会被误报为成功。
20. 数据库记录、Windows 原件、WSL 派生图片之间的引用可核对。
21. 明确并验证完整备份范围，不能只备份数据库。

## 15. 建议实施顺序

每步先写验收测试或检查清单，再进入下一步；不要一次性实现完整 UI。

1. **环境与 DSH API 只读核实**：PostgreSQL、路径、文件选择、Host/Client 通信、slot、图片处理依赖。
2. **冻结最小 DDL 与状态机**：Document/Page/Capture/Asset/Transform，哈希约束，导入失败恢复。
3. **最小插件骨架**：可安装的独立插件页面和 Host 业务服务。
4. **单文件导入纵切面**：选择文件 → SHA-256 → 复制原件 → 数据库记录 → 图库看到原件。
5. **批量与重复导入**：唯一约束、并发保护、错误反馈、待确认恢复。
6. **视觉候选与人工归组**：Page/Capture 关系、并排比较、更换首选照片。
7. **标准化与查看器**：旋转、裁剪、缩放、缩略图、原件对照。
8. **完整验收与备份检查**：使用真实手机照片，包括同页多张、相似不同页和失败中断。

## 16. 后续迭代方向（不在本轮交付）

1. 从 Page 中人工或半自动切分 Question；
2. 印刷题干 OCR，低置信度手写识别始终保留人工校对；
3. 题干、答案、知识点、错因等结构化信息；
4. 复习与简化 SRS；
5. 统计分析及只读 Agent 工具；
6. 更可靠的图像对齐、候选排序和可选自动归组；
7. DuckDB 离线分析（确有需求时）；
8. 独立应用适配。

OCR 结果只能是附加注释，永远不能覆盖图片或把不确定的手写识别静默当成事实。

## 17. 新对话的实施提醒

- 用户当前要求形成设计文档，并不代表已授权安装插件、创建数据库或修改 DSH/PostgreSQL 配置。
- 遵循 DSH 插件开发技能：先 inspection，再选 API；先实现最小可用版本，再视觉完善。
- 使用 `plugin_manager install_bundle` 安装工作区 bundle，不直接修改 profile 的 `package.json` 或 `cordis.patch.yml`。
- 多模型分工可以按 `HANDOFF.md` 使用 Kimi 规划、DeepSeek 执行、GLM 审查，但应先验证小任务流程，不追求无人监督自动化。
- 删除、卸载、停止服务、数据库/配置修改等动作必须先向用户说明后果并取得明确许可。
