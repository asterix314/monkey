## 1. 视觉指纹方案

**dHash64**，零新依赖：

```
magick <file> -colorspace Gray -resize 9x8! -depth 8 gray:-
```

输出恰好 **72 字节**原始灰度（Lead 已实测确认）。Node 侧按行比较相邻像素得 8×8 = 64 bit。

- 存储复用已冻结的 `captures.visual_fingerprint bytea` + `visual_fingerprint_method text`
- `method = 'dhash64'`，写 **8 字节**
- 冻结的 `chk_captures_fingerprint_length` 只对 `phash64` 限长，`dhash64` 走成对约束即可，合规
- **不需要 `sql/004_*.sql`**，`001_schema_v1.sql` 保持冻结

不选 aHash / pHash 的理由：pHash 需 DCT，纯 Node 手写成本高、收益未证实；dHash 对亮度对比度变化比 aHash 稳健，适合手机翻拍。

## 2. 旋转归一化

在 Node 里对同一 72 字节灰度做**纯算术旋转**（行列重映射），0°/90°/180°/270° 各算一个 dHash，候选距离取四方向最小值。

- 零额外 ImageMagick 调用、零依赖
- **只存 0° 那一份**，保证 `visual_fingerprint` 仍是 8 字节单值；比较时在内存现算其余三方向（72 次读字节，可忽略）
- 依据：8 张真实图里确实存在 90° 旋转的情形

## 3. 不裁背景留白

直接整图缩放，保留留白。理由：

- DESIGN §4 第一轮排除自动页面检测，`-trim -fuzz` 本质是页面检测的弱化版
- 对木桌/床单背景、阴影、装订线极不稳定；**裁错会把两张不同页裁成相似小块，反而制造误导候选**
- 第一轮接受召回率上限，靠并排 + 人工确认兜底

⇒ **UI 文案与验收必须如实写明：召回是尽力而为，不是承诺。**

## 4. 候选召回与排序

| 项 | 值 |
|---|---|
| 候选集 | 有指纹的 Capture 所在 Page（含跨分类，同学科同学期优先排序但不排除） |
| 距离 | `min over 4 rotations of popcount64` |
| 强候选 | `distance ≤ 12` 且宽高比兼容 |
| 弱候选 | `13 ≤ distance ≤ 18` 且宽高比兼容 |
| 不进候选 | `distance > 18` |
| 每页代表 | 该页所有 Capture 中距离最小者 |
| 返回上限 | 5 页 |
| 宽高比兼容 | `min(w/h, h/w) ≥ 0.7`（含旋转后对调） |

**阈值依据与风险**：朴素全图 dHash 在 8 张真实图上两两距离 **25–40**，说明 20+ 区间全是噪声，阈值必须压在 ≤18 才有意义；≤12 约对应 80% 位一致，是 dHash 同图经验区间。

**为什么阈值偏紧**：绝不自动合并，阈值偏紧的代价只是漏候选（用户走手动搜索）；阈值偏松会把「相似但不同的练习页」推进前 5 名**误导用户**。**宁可漏、不可错。**

阈值做成常量集中在 `visual-fingerprint.js` 顶部，待真实练习页样本标定后再调。

## 5. 指纹写入时机

- **导入成功后同步算一次**（`registered` 已提交），算完同状态 UPDATE 写回
- **失败只记日志、不阻断导入**——指纹是增强，不是门槛
- 已存在 8 行：**按需补算**——candidates 接口发现某 Capture 无指纹时现场补算并写回
- 不建独立后台任务、不新增回填路由
- `listCaptures` 响应增加 `fingerprintReady` 标志供 UI 提示

理由：指纹耗时 ≈ 一次 72 字节灰度转换，相对导入的复制 + 两次 identify 可忽略。

## 6. 建 Page 时 subject/term 的来源

从 `captures.original_path` 前两段目录名反查 `subjects`/`terms` 字典行取 id，**UI 不传**。

理由：原件路径前两段就是导入时用户选定的分类，且现有 `CAPTURE_SELECT_TEMPLATE` 已这么 join——沿用同一事实来源。字典里查不到则报 `NOT_FOUND`，提示先修分类；本步不提供「建页时改分类」旁路。

## 7. Document / Page 创建参数

每个新 Page 建**独立 Document**：

- `source_type = 'other'`、`title = NULL`、`document_date = NULL`
- `page_number = NULL`（**不自动递增**）
- `status = 'pending'`

理由：DESIGN §8.1 允许「第一轮简单按每次导入或用户整理建立」；`page_number` 可空是 DDL 明示的视觉确认前合法状态，自动递增需要 Document 内顺序，而「同次导入多图属于同一 Document」这条组装规则 DESIGN 明确说不追求。编页码留给第 7 步。

**关键推论：本步 Page 只能是 `pending`** —— `trig_pages_status_transition` 要求 `organized` 必须有 ready 的 standardized asset，那是第 7 步。代码里不碰 `status` 列。

## 9. 图库语义变更（兼容策略）

**不改** `listCaptures`、**不改** `GET /wrongbook/captures` 契约。

新增 `GET /wrongbook/pages` 返回 Page 列表（含首选 Capture、Capture 计数）。Client 图库卡片**改为默认按 Page 渲染**，未归组 Capture 以「待整理」区单列。

## 10. HTTP API 契约

> ⚠️ **Lead 修正**：`dsh-host-webserver` 的 `WebRouteKind` 只有 `'exact' | 'prefix'`，**没有路径参数**（已核实 `lib/types/index.d.ts:35-44`）。`/pages/:id` 这类写法不可实现。
> 因此 `:id` 一律改为 **query 参数**（读）或 **JSON body 字段**（写）。下表已按此修正。

| 方法 | 路径 | 用途 | 契约要点 |
|---|---|---|---|
| GET | `/wrongbook/captures/candidates` | 为某 Capture 检索同页候选 | `?capture_id=<uuid>` 必填。返回 `{ok:true, fingerprintReady, candidateMode:'fingerprint'\|'recent_fallback', items:[{page, preferredCapture, captureCount, score:{distance, aspectRatioDelta, aspectRatioCompatible, kind}, sameClassification}]}`。items ≤5，按 distance 升序。无指纹时 `recent_fallback` 给同学科同学期最近 3 页。**只读** |
| GET | `/wrongbook/pages` | Page 列表 / 手动搜索 | query 全可选：`limit`(≤200) / `subject_code` / `term_code` / `q`。返回 `{ok:true, items:[PageCard]}`。`q` 对 `original_filename`、`documents.title` 模糊（**参数化 + `%`/`_` 转义**）。**只读** |
| GET | `/wrongbook/pages/detail` | 单页 + 全部 Capture | `?page_id=<uuid>`。返回 `{ok:true, page, captures:[presentCapture...按 created_at 升序], preferredCaptureId}`。`NOT_FOUND` 404 |
| POST | `/wrongbook/pages` | **「不同页，创建新页面」** | JSON body `{capture_id}`。事务内建 document+page 并 attach（乐观条件 `page_id IS NULL`）。成功 `{ok:true, outcome:'created', page, capture}`。重复提交 → `CAPTURE_ALREADY_GROUPED` 409（含当前 pageId，UI 据此刷新） |
| POST | `/wrongbook/pages/attach` | **「同一页，添加为另一张照片」** | JSON body `{page_id, capture_id}`。事务：`SELECT capture FOR UPDATE` → 校验 `page_id IS NULL` → UPDATE → 校验目标页仍存在 → commit。`CAPTURE_ALREADY_GROUPED` 409；目标页被删 → 404 |
| POST | `/wrongbook/pages/preferred` | 更换首选 Capture | JSON body `{page_id, capture_id}`。事务：锁 page → 校验 capture 属于本页（不符 `PREFERRED_CAPTURE_NOT_IN_PAGE` 409）→ UPDATE `preferred_capture_id`。**绝不 DELETE 任何 Capture**；不改 `status` |

全部走 `rejected()` 鉴权 + `methodNotAllowed()` + `sendFailure()`。写路由一律 POST + JSON body（不用 PUT/DELETE：本步无删除语义，更换首选是命令式动作）。

**JSON body 是新攻击面**（原 import 走 raw body）：必须有 **≤16KB 上限**（复用 `PAYLOAD_TOO_LARGE`）与非法 JSON 的 400，不能复用 import 的流式哈希路径。

### 并发与幂等

`attach` 用单事务 + `SELECT ... FOR UPDATE` 锁目标 capture 行 + `AND page_id IS NULL` 乐观条件。并发重复归组只有一个成功，另一个得 409。

目标 Page 被并发删除由 `fk_captures_page_id` 的 `ON DELETE RESTRICT` 反向保护：只要还有 Capture 引用，Page 删不掉。

## 11. 更换首选 Capture 的约束

```sql
UPDATE pages SET preferred_capture_id = $1
 WHERE id = $2
   AND EXISTS (SELECT 1 FROM captures WHERE id = $1 AND page_id = $2)
```

`rowCount = 0` 时区分「页不存在」与「capture 不属于本页」返回不同错误码。

`fk_pages_preferred_capture_id` 复合外键本来就强制 `(preferred_capture_id, id)` 命中 `captures(id, page_id)`——「把 A 页 capture 设为 B 页首选」在数据库层必然失败。应用层先查一次只为返回可读错误码而非裸 `23503`。

**不动 captures 任何行、不删文件。**

## 14. 真实数据召回验证（非自动断言）

用真实手机拍 **2 组同页双拍 + 2 组相似不同页练习页** 导入，人工核对：

- 同页对应进入强候选
- 不同页即使版式相似也能点「不同页，创建新页面」保持独立
- 图库只显示一个 Page 且页下两个 Capture
- 更换首选后两原件仍在

现有 8 张老照片**只用于验证管线健壮性**（横向/纵向/大留白都能出指纹或明确降级），**不用于标定阈值**。

## 15. Blockers（待用户裁决）

1. **真实样本缺口**：现有 8 张归档照片均为**翻拍的老黑白家庭合影**，不是数学练习页。没有「同一试卷页两次不同拍摄」的正例对，也没有「版式相似但内容不同的练习页」负例对。因此 DESIGN §14.2-9 要求的「候选召回效果需用真实样本测试」**在本步无法对真实试卷数据下结论**。

2. **样本不足以标定阈值**：可以先用这 8 张做管线健壮性/降级验证（保证「失败时留空、手工路径可用」），但**不能据此冻结阈值与排序权重**。

## 16. 风险

- 召回有效性未标定：阈值 12/18 与宽高比 0.7 是经验初值，真实练习页上可能全漏（用户只能靠手动搜索）。本步可接受此降级，但**交付说明必须写明，不能把「有候选」当成验收通过**。
- dHash 整图方案对「主体只占画面一小块」的翻拍天然不敏感（8 张真实照片正是如此），第 7/8 步再评估。
- 归组写操作会改 `captures.updated_at`（时间戳触发器）；第一轮无依赖该字段的增量同步逻辑。
- `presentCapture` 新增 `fingerprintReady` 属向后兼容扩展，reviewer 需确认无测试对返回对象做严格等值断言。
- 手动搜索的 ILIKE 必须参数化且转义 `%`/`_`，否则用户输入 `%` 会拉全表。
