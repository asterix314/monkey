# 页面合并的相似度依据 — 调研与真实数据实测

> 日期：2026-11-28
> 背景：用户试用第 6 步人工归组后指出「页面图库少时可以人工比较，多了以后纯靠手工不现实」
> 数据：9 张真实一年级数学练习页照片（用户提供），真值 {1,7} {2,8} {4,9} 同页，3/5/6 独立
> 结论：**OCR 文本 + 二元词 Dice 系数完全可分，纯像素路线（含标准化后）全部失败**

---

## 1. 结论先行

| 方案 | 同页最低 | 不同页最高 | 可分？ |
|---|---|---|---|
| dHash 64 bit | 0.42（归一化） | — | ❌ 重叠 |
| dHash 至 16384 bit | — | — | ❌ 重叠 |
| aHash 各分辨率 | — | — | ❌ 重叠 |
| NCC 归一化互相关 | — | — | ❌ 重叠（且反向） |
| 墨迹密度 NCC | 0.345 | 0.835 | ❌ **反向** |
| 行/列投影轮廓 | -0.288 | 0.921 | ❌ 重叠 |
| 标准化（deskew+裁纸）后 NCC | 0.308 | 0.748 | ❌ 重叠 |
| 标准化后低分辨率+模糊 | 0.380 | 0.884 | ❌ 重叠 |
| 方形归一+4方向旋转 | 0.366 | 0.783 | ❌ 重叠 |
| 平移搜索 NCC | 0.132 | 0.808 | ❌ 重叠 |
| **OCR 文本 + Dice 2-gram** | **0.566** | **0.251** | ✅ **完全可分** |

**间隔 0.316，比任何像素方法的「间隔」都大一个量级。**

## 2. 为什么像素方法必然失败（根因）

同一张纸的两次拍摄，差异来自：

1. **透视与旋转**——纸张在画面里的四边形形状不同
2. **背景**——桌面/床单/手/阴影，占画面比例差异极大
3. **光照**——手机自动曝光让同一张纸的绝对亮度差很多
4. **纸张弯曲**——练习页卷曲导致局部几何畸变

而不同练习页之间的差异只是**印刷内容不同**。一旦把两者都压成低分辨率灰度图，
「纸张在画面里的位置和明暗」这类噪声的方差，**大于**「题目文字不同」这类信号的方差。
所以任何基于像素强度/梯度的度量（dHash/aHash/pHash/NCC/SSIM/投影）都在比较错的维度。

**已验证的边界**：
- `-trim` 与 `-fuzz` 在这批图上**完全无效**（都裁不动，输出仍 3072x4096）——桌面亮度接近纸张
- 用投影轮廓自裁纸张可以裁出，但裁完仍然不可分（见上表第 7 行）
- 标准化（deskew + 裁纸 + 统一画布）**没有解决**问题，因为残留的透视和缩放差异仍占主导

**关键洞察**：用户的直觉是对的——「标准化完成后再合并」。但标准化解决的是**人眼可读性**，
不是**机器可比性**。真正让机器可比的不是几何归一，而是**把图像投影成离散符号**（OCR 文本）。

## 3. OCR 方案实测（推荐）

### 3.1 环境与工具

- **已实测可用**：`rapidocr-onnxruntime` 1.2.3 + onnxruntime 1.32.0
- **纯 Python，无需 root**：在用户空间 venv 里 `pip install` 即可（我用 get-pip 引导的 venv 验证通过）
- 模型内置（~14 MB：det 2.4M + cls 572K + rec 11M），**不需要另外下载或联网**
- 支持中文；这批图上的识别质量足以做去重
- **耗时 3–5 秒/张**（CPU，3072×4096 原图）——这是架构决策的关键约束

**对比 tesseract**：系统源里有 `tesseract-ocr 5.5.0` + `tesseract-ocr-chi-sim`，
但**安装需要 root（sudo）**，本会话沙箱内 `sudo` 报 "no new privileges"。
若你愿意在宿主侧装，也可以——但 rapidocr 不需要 root 且中文识别质量通常更好。

### 3.2 算法

```
OCR 提取每页文本 → 分词（汉字单字 / 数字串 / 字母串，去标点空白）
→ 取 2-gram 多重集 → Dice 系数
```

```python
def tokens(t):  return re.findall(r'[\u4e00-\u9fff]|\d+|[a-zA-Z]+', t)

def ngrams(t, n=2):
    tk = tokens(t)
    return Counter(tuple(tk[i:i+n]) for i in range(len(tk)-n+1))

def dice(c1, c2):
    inter = sum((c1 & c2).values())
    total = sum(c1.values()) + sum(c2.values())
    return 2*inter/total if total else 0.0
```

**为什么用 Dice 而不是 difflib.SequenceMatcher**：
OCR 引擎按**检测框顺序**返回文本，不是阅读顺序——同一页两次拍摄的检测顺序可能不同。
`SequenceMatcher` 对顺序敏感，实测同页对只有 0.19–0.58；改成顺序无关的多重集 Dice 后
稳定在 0.57–0.66。这是本次调研最重要的一处实现细节。

**为什么 2-gram**：1-gram 区分度不够（不同页也能到 0.55），
3-gram 太稀疏（OCR 错字会打断）。2-gram 实测间隔最大。

### 3.3 真实数据结果

| 配对 | Dice 2-gram |
|---|---|
| 2-8（同页） | **0.6622** |
| 1-7（同页） | **0.6241** |
| 4-9（同页） | **0.5663** |
| 3-5（同单元相邻页，最难的负例） | 0.2507 |
| 3-6 | 0.2262 |
| 1-3 | 0.2189 |
| 1-2（同单元相邻页） | 0.2126 |
| 其余 29 个负例 | ≤ 0.192 |

**阈值敏感性**：

| 阈值 | 召回 | 误报 |
|---|---|---|
| 0.30 | 3/3 | 0/33 |
| 0.35 | 3/3 | 0/33 |
| 0.40 | 3/3 | 0/33 |
| 0.45 | 3/3 | 0/33 |
| 0.50 | 3/3 | 0/33 |

阈值 0.30–0.50 **全域安全**。建议取 **0.40**（约等于 0.566 与 0.251 的中点）。
但注意：9 张样本仍然太小，**不能当作最终阈值标定依据**，只能说「这个量级成立」。

### 3.4 原始 OCR 文本（留档）

见 `docs/research/ocr-samples-9pages.json`。示例（4 与 9 是同一页）：

```
4: ...数学练习（一）...1、比10小，比6大的数有...2、下面的算式中，得数最大的是...
   5、一盘桃子吃了2个，还剩6个，盘子里原来有...6、如图，桌上有3盘梨...
9: 数学练习（一）一、填空...1、比10小，比6大的数有...2、下面的算式中，得数最大的是...
   5、一盘桃子吃了2个，还剩6个，盘子里原来有...
```

两段文字语义完全对应，但**段落顺序和字符顺序都不同**——这正是必须用顺序无关度量的原因。

## 4. 架构影响：OCR 必须异步

3–5 秒/张 × 一次导入 10 张 = 30–50 秒。**不能同步阻塞导入**。

建议：
- 导入时仍只做 SHA-256 + 归档 + 登记（现在的行为，不变）
- OCR 与指纹**异步后台计算**，写回 `captures.visual_fingerprint` / 新表
- 归组界面显示「正在分析…」状态，算完再给候选

这与用户提出的「先全部导入成新页面，标准化后再合并」是一致的：
导入阶段不做任何相似性判断，合并阶段才有完整数据可用。

## 5. 与用户方案的关系

用户提出三步：
1. **先全部导入成新页面（除非 hash 相同）** ← 与现状一致，`createPage` 逐张建页
2. **标准化（剪裁、旋转）完成后** ← DESIGN 第 7 步
3. **再进行合并（自动判断 + 人工确认）** ← 本方案

**建议的调整**：合并**不必等标准化完成**。OCR 直接吃原件就够了（实测就是在原件上跑的），
而标准化（人眼可读性）是独立的一步。把合并排在标准化之后会无谓地推迟一个高价值功能。
但如果你坚持先做标准化，也可以——OCR 路径两者都成立。

## 6. 需要用户决策

1. **是否接受 OCR 方案**（vs 继续找视觉方案）。视觉方案已用 10 种方法在真实数据上证伪。
2. **OCR 引擎选型**：
   - `rapidocr-onnxruntime`（推荐）：无 root、纯 Python、模型内置、中文好；但 502 MB 依赖体积
   - `tesseract`：需 root 装系统包（约 30 MB），体积小；中文识别质量通常弱于 PaddleOCR 系
3. **OCR 依赖装在哪里**：
   - 用户空间 venv（工作区内，`data/ocr-venv`）——不改系统
   - 还是你在宿主侧装 tesseract / 或在系统 Python 装
4. **异步架构**：是否接受「导入完成 ≠ 可合并」，OCR 后台跑

## 7. 尚未验证

- **样本量**：只有 3 组正例、33 个负例，且全部来自同一批拍摄（同一天、同一部手机、同一桌面）。
  跨设备、跨光照、跨纸张的鲁棒性未验证。
- **OCR 失败场景**：模糊照片、纯图形页（无文字）会 OCR 出空串。空串之间的 Dice 无意义，
  必须显式处理（「无文字页不参与文本比对」）。
- **手写内容**：一年级练习页有大量铅笔手写。OCR 主要识别印刷体，手写部分会大量丢失或误识。
  这对「同页判定」影响不大（同页的手写也相同），但对「同一页不同作答」的情形需要人工确认——
  这恰好符合 DESIGN §11.2「不能仅凭相似度自动合并」。
